# WorldGen Terrain System — Spec Sheet + Implementation Plan

**Project:** Modular 3D world generator  
**Engine target:** Godot 4.6  
**Approach:** Custom terrain architecture, not locked to one game and not dependent on Terrain3D  
**Primary design goal:** Infinite terrain that can be shaped by real DEM data, then extended procedurally forever.

---

## 0. Core Direction

This restart should be deliberately small at first.

The first target is not a full world generator. The first target is:

> Infinite terrain chunks using a clean height provider.

Everything else hangs off that.

The terrain system should be built as a reusable module that can be dropped into different projects. It should not know about player stats, quests, settlements, combat, vehicles, save systems, or any specific game rules.

### 0.3 2026-05-25 Clipmap Roadmap Reset

The recent clipmap work produced one important rule: do not hide clipmap
problems with whole-page alpha fades or broad fog. Those fixes make the square
page/ring footprint visible and create a different failure mode.

Current accepted clipmap transition policy:

```text
geometry: opaque page/ring meshes only
height recenter smoothing: world-space previous/current height-page blend
LOD transition smoothing: shader coarse/fine morph only in the transition band
sampling: page origins/extents are world-space and stable
fog/visibility: edge-only, used only to hide the outer loaded boundary
near/far handoff: tested height continuity stays mandatory
known residual: subtle far/LOD quality shifts can still appear in the interim renderer
policy: fix black holes, hard seams, crashes, and review blockers immediately; route remaining subtle shifts into the GPU-resident page/ring renderer instead of patching the interim path
```

Immediate roadmap order from here:

```text
1. Add a motion/recenter profiler gate for the walk preview. Current guide:
   `plans/runtime_motion_profile_guide.md`.
2. Add one TerrainQualityProfile source of truth for near window, far levels,
   fog edge, worker budget, and camera distance. Current guide:
   `plans/terrain_quality_profile_guide.md`.
3. Keep visibility/fog as a pass/fail contract, not a screenshot-only tune.
   Current report:
   `factory/runtime/godot_visibility_contract/visibility_contract_report.json`.
4. Use the profiler to decide whether remaining hitching is frame-time work,
   visual recenter snap, or LOD/material change.
5. If it is frame-time work, keep fixing scheduling/prefetch/cache pressure first.
6. If it is visual snap or subtle quality drift, keep aligning with the World 4
   pattern: stable GPU-resident page geometry, previous/current height pages,
   coarse/fine shader morph, and no broad fog/alpha cover-up.
7. Move far clipmap pages toward GPU residency behind the same provider/page
   contract after the CPU/native facts remain stable.
8. Keep landform scale profiles review-only until biome/material context exists; use the live tour for relative comparison, not default promotion.
9. Keep pass/corridor live streaming review tabled until the native/GPU-page path is visually stable enough at full landform-tour scale; use the static visual artifact as the current shaping proof.
10. Continue hydrology/rivers before erosion.
11. Add biome/material masks only after height clipmap motion and base world facts are accepted.
```

## 1. Core Principles

### 1.1 Terrain mesh is disposable

The mesh is just the visible surface. It can be rebuilt, swapped, simplified, hidden, or replaced.

The important thing is the terrain data model:

```text
height
slope
curvature
source confidence
DEM source information
roughness
flow direction
flow accumulation
river likelihood
biome hints later
```

### 1.2 Height provider comes before features

Every terrain chunk asks the same question:

```text
height = sample_height(world_x, world_z)
```

The chunk does not care whether the answer comes from noise, a DEM, a blended DEM pyramid, a river carving pass, erosion, or a future ML model.

### 1.3 DEMs are informants, not the world itself

OpenTopography DEMs should not become one-to-one game terrain chunks. They should become terrain facts and terrain examples.

A DEM can provide:

```text
real height shape
ridge/valley structure
slope patterns
roughness patterns
watershed structure
terrain kernels for procedural expansion
```

The infinite world uses those facts to make believable terrain beyond the DEM boundaries.

### 1.4 Visual checkpoints over heavy test suites

Use debug views, overlays, screenshots, and simple movement tests first.

The project should avoid becoming a massive code-testing project too early.

### 1.5 Add systems in order

Do not build rivers before hydrology hints.  
Do not build erosion before stable terrain and water flow.  
Do not build textures before height terrain works.

The order is:

```text
1. Infinite terrain chunks
2. Clean height provider
3. DEM sampling
4. DEM resolution blending
5. Procedural infinite fill
6. Hydrology hints
7. Rivers
8. Erosion
```

## 2. High-Level Architecture

```text
WorldGenTerrain
│
├── TerrainWorld
│   ├── Owns the terrain system root
│   ├── Tracks viewer/camera/player position
│   ├── Updates streamer
│   └── Exposes debug controls
│
├── TerrainStreamer
│   ├── Decides which chunks should exist
│   ├── Assigns LOD levels
│   ├── Queues chunk builds
│   ├── Recycles old chunks
│   └── Keeps chunk count bounded
│
├── TerrainChunk
│   ├── MeshInstance3D wrapper
│   ├── Stores chunk coordinate and LOD
│   ├── Receives generated mesh
│   └── Optional debug metadata
│
├── TerrainMeshBuilder
│   ├── Builds vertices
│   ├── Builds normals
│   ├── Builds index arrays
│   ├── Builds skirts or seam helpers
│   └── Returns mesh array data
│
├── TerrainHeightProvider
│   ├── Samples height at world coordinates
│   ├── Blends procedural terrain and DEM data
│   ├── Provides source confidence
│   └── Later provides slope/flow/river facts

├── DEM System
│   ├── DEM importer / offline converter
│   ├── DEM tile sets
│   ├── DEM metadata
│   ├── DEM pyramids

│
└── Hydrology / Rivers / Erosion
    ├── Flow hints
    ├── River graph
    ├── Channel carving
    └── Erosion passes
```

## 4. Shared Runtime Concepts

### 4.1 World coordinates

Terrain uses meter-based coordinates:

```text
world_x = meters east/west
world_z = meters north/south
height_y = meters up/down
```

Do not render directly in latitude/longitude.

DEM projection, CRS, vertical datum, and geospatial conversion should live in an offline import/conversion stage, not inside the terrain chunk renderer.

### 4.2 Chunk coordinate

Chunks are addressed by integer coordinates:

```text
chunk_coord = Vector2i(chunk_x, chunk_z)
```

Given a fixed chunk size:

```text
chunk_origin_x = chunk_coord.x * chunk_size_m
chunk_origin_z = chunk_coord.y * chunk_size_m
```

### 4.3 Fixed chunk size, variable LOD density

Use fixed world-size chunks. Change the number of vertices by LOD.

Recommended first settings:

```text
chunk_size_m = 2048
LOD 0: 129 x 129 vertices, 16m spacing
LOD 1: 65 x 65 vertices, 32m spacing
LOD 2: 33 x 33 vertices, 64m spacing
LOD 3: 17 x 17 vertices, 128m spacing
```

This keeps chunk placement simple.

Treat 257 x 257 LOD0 as the high-detail candidate after threaded/native mesh
building is stable. Larger chunks make landforms read as continuous terrain
instead of many small adjacent tiles, so lower vertex density before shrinking
chunks.

### 4.4 First seam strategy

Use terrain skirts first.

A skirt is a small vertical wall around the chunk edge that hides tiny cracks between different LODs.

Do not start with complicated transition meshes. They can come later.

Skirts are only a visual fallback. They are not the seam solution.

The real seam contract is:

```text
shared edges sample identical world coordinates
height providers are deterministic
no per-chunk height normalization
no per-chunk random offsets
DEM/procedural blends are evaluated in world space
chunks build from padded height grids when filters need neighbors
only interior samples are modified by smoothing, erosion, or edge ramps
automated seam checks compare neighbor edge heights directly
```

The first implementation can show skirts, but it still needs a seam metric.

Current Godot status:

```text
opt-in mesh skirts exist on TerrainWorldNode
walk preview now retains 7 x 7 chunks using skirted ring LOD density
near 3 x 3 chunks stay at 129 x 129 vertices / 4m spacing
outer rings use 65 x 65 and 33 x 33 vertices to keep broader terrain cheap
height seam checks remain the real authority; skirts only hide renderer cracks
```

### 4.5 Terrain sample

The height provider should eventually return more than a float.

Early version:

```gdscript
height_provider.sample_height(world_x, world_z) -> float
```

Future version:

```gdscript
height_provider.sample(world_x, world_z) -> TerrainSample
```

Conceptual `TerrainSample`:

```text
height: float
normal: Vector3 optional
slope: float optional
curvature: float optional
source_confidence: float
source_mask: int
source_resolution_m: float
flow_direction: Vector2 optional
flow_accumulation: float optional
river_likelihood: float optional
```


## Implementation Steps

### Step 1.1 — Create TerrainWorld

`TerrainWorld` is the root node for the terrain module.

Responsibilities:

```text
holds terrain settings
holds height provider reference
holds streamer reference
tracks viewer position
updates terrain streamer
owns debug mode state
```

Suggested exported settings:

```gdscript
@export var viewer_path: NodePath
@export var chunk_size_m: float = 2048.0
@export var visible_radius_chunks: int = 4
@export var max_lod: int = 4
@export var build_budget_per_frame: int = 2
@export var debug_enabled: bool = true
```

### Step 1.2 — Create TerrainStreamer

`TerrainStreamer` calculates which chunk coordinates should exist.

Each update:

```text
get viewer world position
convert to current chunk coordinate
calculate visible chunk square/radius
assign LOD by distance
create missing chunks
queue mesh builds
retire chunks outside radius
```

Basic LOD rule:

```text
distance 0-1 chunks: LOD 0
distance 2 chunks:   LOD 1
distance 3 chunks:   LOD 2
distance 4 chunks:   LOD 3+
```

Use Chebyshev distance for a square ring:

```gdscript
var dx = abs(chunk_coord.x - viewer_chunk.x)
var dz = abs(chunk_coord.y - viewer_chunk.y)
var ring = max(dx, dz)
```

### Step 1.3 — Create TerrainChunk

A chunk is a lightweight node containing:

```text
MeshInstance3D
chunk coordinate
LOD level
current build state
optional debug label/metadata
```

Chunk states:

```text
Missing
Queued
Building
Ready
Retiring
```

### Step 1.4 — Create TerrainMeshBuilder

The mesh builder receives:

```text
chunk_coord
LOD
chunk_size_m
height_provider
settings
```

It returns mesh arrays:

```text
vertices
normals
uvs optional
indices
debug colors optional
```

Mesh generation loop:

```gdscript
for z_i in range(vertex_count):
    for x_i in range(vertex_count):
        var local_x = x_i * spacing
        var local_z = z_i * spacing
        var world_x = chunk_origin_x + local_x
        var world_z = chunk_origin_z + local_z
        var height = height_provider.sample_height(world_x, world_z)
        vertices.append(Vector3(local_x, height, local_z))
```

Important rule:

> Shared edges must sample identical world coordinates.

### Step 1.5 — Add debug material

Start with a plain material.

Useful debug modes:

```text
solid gray
chunk coordinate color
LOD ring color
height bands
wireframe overlay
seam view
```

## Visual Checkpoint

The phase passes when:

```text
you can move the viewer in any direction
chunks appear ahead and disappear behind
chunk count stays bounded
LOD rings are visible in debug mode
no huge cracks appear
no obvious chunk origin mistakes happen
```

## Stop Condition

Stop Phase 1 as soon as infinite chunks work with a simple height source.

Do not add DEMs yet.

## Core Interface

First-pass provider:

```gdscript
class_name TerrainHeightProvider
```

```gdscript
func sample(world_x: float, world_z: float) -> Dictionary:
```


Combines multiple height sources.

Early structure:


## DEM Sampler


# Phase 4 — DEM Resolution Blending

## Goal

Make different-resolution DEM sources work together without ugly borders, cliffs, or mesh seams.

This is one of the most important phases.

## Scope

Included:

```text
multiple DEM tile sources
resolution metadata
DEM pyramid concept
source priority
confidence blending
edge fading
residual detail blending
debug comparison views
```

Not included:

```text
procedural terrain kernels
rivers
erosion
biomes
textures
```

## Problem

Different DEMs may have different:

```text
sample spacing
accuracy
bounds
vertical datum
no-data areas
noise level
surface type: DTM vs DSM
```

Never let terrain chunks directly decide which DEM they are using.

Chunks still only ask:

```text
height_provider.sample_height(world_x, world_z)
```

## Required Metadata

Each DEM source should track:

```text
source_id
source_name
source_resolution_m
source_priority
is_dtm_or_dsm
horizontal_units
vertical_units
bounds_m
no_data_mask
confidence
import_date optional
```

## Blending Strategy

### 4.1 Base height layer

Use the broadest reliable terrain source as base height.

Example:

```text
90m or 30m DEM gives broad landform
```

### 4.2 High-resolution residual layer

High-res DEM should contribute detail, not completely fight the base.

Concept:

```text
low_res_height = sample_low_res_source(x, z)
high_res_height = sample_high_res_source(x, z)
residual = high_res_height - low_res_height
final = low_res_height + residual * high_res_confidence
```

This helps the high-resolution data fade naturally at its boundary.

### 4.3 Confidence fade

High-res confidence should fade near:

```text
source boundary
no-data holes
known bad data
steep mismatch zones
```

Example:

```text
confidence = source_confidence * edge_fade * no_data_validity * quality_weight
```

### 4.4 Priority stack

If two sources overlap:

```text
prefer cleaner DTM over DSM for bare earth
prefer higher resolution if confidence is high
prefer lower resolution if high-res data is noisy or partial
```

Do not always blindly choose highest resolution.

## DEM Pyramid

Create a pyramid for each source:

```text
LOD 0: native or near-native resolution
LOD 1: 2x downsampled
LOD 2: 4x downsampled
LOD 3: 8x downsampled
```

The height provider chooses an appropriate sampling level based on requested terrain LOD or desired sample spacing.

Important:

> Terrain mesh LOD and DEM source LOD are related, but they are not the same thing.

A far chunk can sample low-detail DEM data. A near chunk can sample high-detail data.

## Seam Rule

The same world coordinate must produce the same height regardless of which chunk asks for it.

That means:

```text
sample_height(1000, 2000) returns the same value for every chunk, every time
```

## Visual Checkpoint

The phase passes when:

```text
a lower-resolution DEM and a higher-resolution DEM overlap
high-res detail appears where available
high-res detail fades out smoothly
no obvious cliffs appear at DEM borders
no-data holes do not create spikes
chunk LOD changes remain acceptable
```

## Stop Condition

Stop Phase 4 when mixed DEM resolutions look clean enough in plain gray terrain.

Do not add biomes or textures to hide issues.

## Why This Comes Before Rivers

Rivers need to know where water would naturally collect.

Hydrology hints answer:

```text

```

## Input Data

Hydrology can use:

```text
height
slope
curvature

```

## Chunk Padding Requirement

Hydrology cannot only look at the visible chunk interior.

It needs padded sampling around the chunk:

```text
chunk area + margin
```

Example:

```text
for a 2048m chunk, sample an extra 256m to 1024m border
```

This prevents flow from breaking at chunk boundaries.

## First Algorithms

Keep it simple.

### Slope direction

Calculate downhill direction from neighboring height samples.

### Flow accumulation approximation

At a low resolution, accumulate water from higher cells to lower cells.

### Wetness score

Concept:

```text
wetness = flow_accumulation / max(slope, small_value)
```

### Channel likelihood

Concept:

```text
river_likelihood = high flow accumulation + suitable valley shape
```

```text

hydrology hints
river paths
```

If erosion comes too early, it can hide or complicate basic terrain problems.

## Erosion Strategy

Use three levels of erosion, in this order.

### 8.1 DEM-derived erosion detail

Extract erosion-like detail from real DEMs:

```text
small channels
ridge roughness
slope break patterns
valley textures
alluvial fan patterns if available
```

Use these as procedural residuals in similar terrain types.

This makes terrain look eroded without running a heavy simulation.

### 8.2 Thermal erosion

Thermal erosion smooths slopes that are too steep.

Useful for:

```text
talus slopes
cliff bases
mountain sides
mesa edges
```

Simple rule:

```text
if slope is above talus angle:
    move some height from high cell to low neighboring cell
```

Run on terrain tiles with padding so chunk edges stay consistent.

### 8.3 Hydraulic-inspired erosion

Do a simplified water-flow erosion pass using hydrology hints.

Concept:

```text
where flow accumulation is high:
    cut slightly into terrain
where slope decreases near channels:
    deposit slightly
```

This is not full fluid simulation. It is a shaping pass.

## Runtime vs Offline

Prefer erosion as an offline or cached generation pass.

Runtime terrain chunks should sample the result, not run expensive erosion from scratch every frame.

Potential approach:

```text
for each large terrain region:
    build base height field
    apply hydrology hints
    apply river carving
    apply erosion shaping
    cache result
chunks sample from cached region data
```

## Edge Safety

Erosion must not break chunk seams.

Rules:

```text
run erosion on larger region tiles, not individual visible chunks
use padding around each region
crop final result back to region bounds
shared world coordinate must still return same height
```

## Debug Views

```text

```

## Visual Checkpoint

The phase passes when:

```text

no chunk-edge erosion artifacts appear

```

## Stop Condition

Stop Phase 8 when erosion improves the terrain without becoming the whole project.

# Optimization Track — Clipmaps, Streaming, and Long-Term Performance

This is not a new feature phase that should happen before terrain works. It is a parallel architecture track that keeps the system future-proof.

The core rule is:

```text
Start with chunked terrain.
Design so the renderer can later be swapped for clipmaps or hybrid terrain.
```

## Why Not Start With Clipmaps Immediately?

Geometry clipmaps are powerful, but they combine several hard problems at once:

```text
LOD transitions
height sampling
viewer-centered ring updates
GPU-friendly mesh reuse
collision separation
shader blending
streaming/caching
```

That is too much for the first restart pass.

The first pass should prove:

```text
height provider works
infinite coordinates work
chunks stream correctly
DEM blending works
terrain looks good in plain gray
```

Once that foundation works, clipmaps become much safer to add.

## Renderer Abstraction

Add a renderer interface so terrain generation is not locked to chunk meshes.

Conceptual interface:

```gdscript
class_name TerrainRenderer
extends Node

func set_height_provider(provider: TerrainHeightProvider) -> void:
    pass

func set_settings(settings: TerrainSettings) -> void:
    pass

func sync_viewer(world_position: Vector3) -> void:
    pass

func set_debug_mode(debug_mode: int) -> void:
    pass
```

Then the system can support multiple renderers:

```text
ChunkTerrainRenderer      # first implementation
ClipmapTerrainRenderer    # later visual terrain renderer
HybridTerrainRenderer     # likely long-term winner
```

`TerrainWorld` should talk to `TerrainRenderer`, not directly to chunk-specific code.

## Renderer V1 — Chunked Terrain

This is the first implementation.

Characteristics:

```text
fixed-size chunks
ArrayMesh per chunk
LOD by chunk ring
skirts for cracks
CPU-built mesh arrays
simple debug material
```

Strengths:

```text
easy to understand
easy to debug
works with collision chunks
works with DEM sampling
works with hydrology/rivers later
modular and flexible
```

Weaknesses:

```text
many mesh rebuilds
many nodes if radius gets large
LOD transitions can be chunky
far terrain can become expensive
```

Use this until the height system and DEM system are proven.

## Renderer V2 — Geometry Clipmap

A geometry clipmap uses nested square grids around the viewer.

Concept:

```text
near ring: small spacing, high detail
middle ring: larger spacing
far ring: very large spacing
```

Example:

```text
Level 0: spacing 8m, covers nearby area
Level 1: spacing 16m
Level 2: spacing 32m
Level 3: spacing 64m
Level 4: spacing 128m
```

Each level is a grid or ring centered around the viewer. As the viewer moves, the grid origin snaps to that level's spacing and only the changed edge data needs to update.

Clipmap goals:

```text
stable terrain vertex count
fewer chunk rebuilds
smoother far-distance LOD
large visible terrain range
better long-distance silhouettes
```

Clipmap challenge:

```text
collision, rivers, gameplay, and region data still need chunk/region logic
```

That means clipmap should be treated as a visual renderer, not the whole world system.

## Recommended Long-Term Renderer: Hybrid

The best long-term setup is probably hybrid:

```text
near gameplay area: chunked terrain
far visual terrain: clipmap rings
```

Near chunks handle:

```text
collision
foot placement
physics
rivers close to player
interactive terrain queries
debug chunk inspection
```

Far clipmap handles:

```text
mountain silhouettes
large visible horizon
far valleys
low-cost distant terrain
```

This avoids forcing clipmaps to solve gameplay/collision problems.

## Clipmap Design Requirements

A future `ClipmapTerrainRenderer` should use the same height provider.

The clipmap renderer should ask:

```text
sample = height_provider.sample(world_x, world_z)
```

It should not know about DEM files, biomes, rivers, or erosion internals.

Required clipmap concepts:

```text
clipmap_level
sample_spacing_m
ring_extent_m
viewer_snapped_origin
transition_band_width
height_texture_or_height_buffer
normal_texture_or_shader_normals
```

Each clipmap level should snap its origin to its spacing:

```text
snapped_x = floor(viewer_x / spacing) * spacing
snapped_z = floor(viewer_z / spacing) * spacing
```

This prevents constant tiny updates when the camera moves by fractions of a meter.

## Clipmap Transition Strategy

The transition between one clipmap level and the next should not pop.

Use a transition band near the outer edge of each finer level:

```text
near center: use fine height
near outer band: morph toward coarser height
```

Conceptual blend:

```text
fine_height = sample_height(x, z, fine_spacing)
coarse_height = sample_height(x, z, coarse_spacing)
t = transition_band_factor
height = lerp(fine_height, coarse_height, t)
```

This is similar to the earlier DEM residual idea:

```text
coarse shape stays stable
fine detail fades in/out smoothly
```

## Optimization Order

Do not optimize everything at once.

Use this order:

```text
1. Correct terrain
2. Stable streaming
3. Bounded chunk count
4. Mesh build budget
5. Cache repeated work
6. Thread heavy generation
7. Reduce draw calls
8. Improve far terrain with clipmaps
9. Move selected work to GPU if needed
```

## Performance Budgets to Track Early

Add a simple debug stats overlay.

Track:

```text
visible chunk count
queued mesh jobs
mesh builds per frame
average mesh build time
height samples per second
height provider cache hit rate
DEM tile cache hit rate
active DEM tiles
terrain memory usage
terrain draw calls
main thread frame time
worker thread time
stale/cancelled jobs
```

These numbers matter more than guessing.

## CPU Optimization

Early CPU wins:

```text
reuse chunk nodes
reuse mesh arrays where possible
cache index buffers per LOD
cache UVs per LOD
cache local vertex x/z positions per LOD
build normals from height samples efficiently
avoid per-vertex object churn where possible
limit chunk builds per frame
cancel jobs for chunks that are no longer needed
prioritize nearby chunks first
```

The mesh builder should separate reusable layout data from per-chunk height data.

Reusable per LOD:

```text
local x/z grid positions
index buffer
uvs
debug layout
skirt indices
```

Per chunk:

```text
world origin
height values
final vertex y values
normals
colors/debug data
```

## Threading Strategy

Worker threads should generate data, not manipulate active scene nodes.

Safe pattern:

```text
worker thread:
    sample height provider
    build height grid
    build vertices
    build normals
    build index/color data
    return mesh arrays

main thread:
    create/update ArrayMesh
    assign to MeshInstance3D
    add/remove/recycle nodes
```

Avoid having worker threads directly modify the active scene tree.

## Streaming Optimization

Streaming should become a priority queue.

Priority factors:

```text
distance to viewer
viewer movement direction
LOD level
whether chunk is currently visible
whether old lower-LOD version already exists
whether chunk is needed for collision
```

Useful behavior:

```text
build nearest missing chunks first
keep old mesh visible until replacement is ready
cancel far jobs when viewer changes direction
preload ahead of fast-moving viewer
throttle generation during frame spikes
```

## DEM / Data Cache Optimization

DEM data should be cached separately from visual chunks.

Caches:

```text
DEM tile cache
DEM pyramid cache
height sample cache
region terrain cache
hydrology cache
river graph cache
erosion result cache
```

Use LRU-style eviction for loaded DEM/region data.

The renderer should be allowed to forget meshes without losing terrain facts.

## Collision Optimization

Do not create collision for every visible chunk.

Use separate collision rules:

```text
collision radius smaller than visual radius
collision LOD lower than visual near LOD if acceptable
collision updates less often than visual terrain
collision generated only around player/gameplay actors
```

Possible setup:

```text
visual radius: 4 to 8 chunks
collision radius: 1 to 2 chunks
far clipmap: visual only, no collision
```

## Floating Origin / Precision

For a truly infinite world, add floating origin support later.

Problem:

```text
very large world coordinates eventually reduce floating point precision
```

Solution:

```text
keep terrain sampling in stable world coordinates
periodically shift visible scene nodes back near origin
track global world position separately from local render position
```

Important distinction:

```text
global terrain coordinate: permanent, deterministic
local render coordinate: shifted for precision
```

The height provider should use global coordinates. Mesh vertices can be local to shifted scene origin.

## GPU Optimization Path

Do not start here, but design toward it.

Possible future path:

```text
CPU chunk meshes
→ cached CPU meshes
→ threaded CPU meshes
→ hybrid chunk + clipmap
→ clipmap height textures
→ shader displacement / GPU normal generation
→ compute-assisted terrain data if needed
```

GPU work makes sense when:

```text
CPU mesh building becomes the bottleneck
far terrain needs huge draw distance
height sampling can be represented as textures/buffers
the terrain renderer is stable enough to justify complexity
```

## RenderingServer Path

Godot's `RenderingServer` can bypass much of the Node system, but it should be treated as a later optimization.

Use normal nodes first:

```text
TerrainChunk as Node3D
MeshInstance3D child
ArrayMesh resource
```

Consider `RenderingServer` later only if profiling shows that node overhead or scene-tree operations are the bottleneck.

## HLOD and Visibility Ranges

Use Godot visibility ranges mainly for non-terrain systems later:

```text
rocks
foliage
settlements
props
far impostors
river detail meshes
```

For terrain itself, custom chunk/clipmap LOD is still the better core approach because terrain LOD must match height sampling, seams, collision, DEM confidence, rivers, and erosion.

## Optimization Stop Rule

Only optimize when one of these is true:

```text
frame time is bad
chunk streaming stutters
memory grows without bound
terrain pops badly
far terrain range is too small
DEM sampling is too slow
collision generation is too slow
```

Otherwise, keep building the core phases.

## Best Practical Long-Term Plan

Use this renderer evolution:

```text
V1: chunked terrain renderer
V1.5: optimized chunk renderer with job queue + caches
V2: hybrid renderer with chunks near player and clipmap far away
V3: GPU-assisted clipmap if profiling proves it is needed
```

The architecture should prepare for clipmaps now, but implementation should wait until after the height provider, DEM sampling, and DEM blending are stable.

# Biome Planning Track — Data Channels Now, Biomes Later

Biomes should be planned for now, but not implemented as a full feature during the first terrain phases.

The rule is:

```text
Reserve biome data channels early.
Do not build biome visuals, ground textures, foliage, or ecology until terrain + hydrology are stable.
```

This keeps the system future-proof without turning Phase 1 into a full world simulation.

## Main Decision

Biomes should not live inside the terrain mesh builder.

They should be resolved from reusable world facts:

```text
height terrain
+ slope/curvature
+ hydrology/wetness
+ climate fields
+ terrain region style
+ DEM/kernel hints
= biome weights
```

The terrain renderer should not decide biomes. It should only display whatever debug or material data the biome system later provides.

## When Biomes Actually Arrive

Recommended order:

```text
Phase 1: no biomes
Phase 2: reserve TerrainSample / WorldFact fields
Phase 3: DEM can provide rough terrain facts
Phase 4: DEM resolution blending stays height-focused
Phase 5: add early climate/region placeholders
Phase 6: hydrology creates real wetness/drainage data
Phase 7: rivers create river, floodplain, wetland context
Phase 7.5: biome resolver debug colors
Phase 8: erosion improves terrain facts used by biomes
After Phase 8: textures, foliage, ecology, gameplay spawning
```

A simple biome debug overlay can appear before erosion, but final biome presentation should wait until the world facts are better.

## Why Not Build Biomes Immediately?

Early biome work creates pressure to add:

```text
textures
foliage
ground cover
weather
animals
resources
settlements
materials
splat maps
```

That would pull the restart away from the main goal: stable infinite terrain.

However, not planning for biomes at all would be a mistake because later systems need shared data channels.

The safe compromise is:

```text
architect for biomes now
implement biome visuals later
```

## Practical Takeaway

Biomes are not hard to add separately if the terrain system already exposes world facts.

